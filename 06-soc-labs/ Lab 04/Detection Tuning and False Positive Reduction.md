# EDR Lab 04 — Detection Tuning and False Positive Reduction

## 1. Objective

Improve an existing Wazuh detection rule by identifying specific Windows user account enumeration commands.

The laboratory focused on detection refinement, troubleshooting, regular expression analysis, and positive and negative testing.

## 2. Lab Environment

- **SIEM:** Wazuh 4.14.10
- **Operating System:** Ubuntu Server 24.04 LTS
- **Monitored Endpoint:** Windows 11 Home
- **Endpoint Telemetry:** Microsoft Sysmon
- **Event ID:** 1 — Process Creation
- **Parent Detection Rule:** 100100
- **Refined Detection Rule:** 100101
- **Alert Level:** 8

## 3. Initial Problem

The previously developed Rule 100100 successfully detected executions of `net.exe` and `net1.exe`.

However, it generated alerts for different commands, regardless of their purpose.

The objective of this laboratory was to introduce a more specific rule that would detect Windows user account enumeration commands.

The new detection needed to distinguish between:

**Relevant command:**

```powershell
net user
```

**General utility command:**

```powershell
net help
```

Both commands may execute the same Windows utilities, but they represent different operations.

## 4. Detection Rule Development

The new rule was created with Rule ID 100101.

It used the existing Rule 100100 as a prerequisite and introduced an additional condition based on the command-line field.

### Initial Detection Logic

The initial expression expected the executable name to be followed by the `user` argument.

However, the rule did not generate the expected alert during testing.

Wazuh continued to generate alerts from Rule 100100.

## 5. Troubleshooting Investigation

### Step 1 — Verify Event Collection

The original Rule 100100 continued generating alerts after the test command was executed.

This indicated that:

- Sysmon was recording process creation events.
- The Wazuh Agent was forwarding relevant telemetry.
- The Wazuh Manager was processing the events.
- The existing custom detection was operational.

The problem was therefore investigated as a detection-matching issue.

### Step 2 — Inspect the Original Event

A Wazuh alert was opened in JSON format.

The following fields were examined:

- `win.eventdata.image`
- `win.eventdata.commandLine`
- `win.eventdata.parentImage`
- `win.eventdata.integrityLevel`
- `win.system.eventID`

The event contained the command line:

```text
"C:\WINDOWS\system32\net.exe" user
```

The parent process was:

```text
powershell.exe
```

The event was generated by Sysmon Event ID 1.

### Step 3 — Identify the Matching Problem

The investigation identified two important command-line formatting differences.

First, some observed command lines used the executable name without the `.exe` extension:

```text
C:\WINDOWS\system32\net1 user
```

Second, other command lines included a closing quotation mark after the executable path:

```text
"C:\WINDOWS\system32\net.exe" user
```

The initial regular expression did not account for both formats.

As a result, the refined detection failed to match the observed events.

## 6. Corrected Detection Rule

The final rule used the following configuration:

```xml
<rule id="100101" level="8">
  <if_sid>100100</if_sid>
  <field name="win.eventdata.commandLine" type="pcre2">(?i)\bnet1?(?:\.exe)?"?\s+user(?:\s|$)</field>
  <description>EDR Lab 04: Windows user account enumeration command detected</description>
  <group>account_discovery,process_creation,</group>
</rule>
```

### Regular Expression Explanation

| Expression | Purpose |
|---|---|
| `(?i)` | Case-insensitive matching |
| `\bnet1?` | Matches `net` or `net1` |
| `(?:\.exe)?` | Makes the `.exe` extension optional |
| `"?` | Allows an optional closing quotation mark |
| `\s+user` | Matches whitespace followed by `user` |
| `(?:\s\|$)` | Requires whitespace or the end of the command |

The expression was designed to match the observed command-line formats in the laboratory.

## 7. Validation and Deployment

The updated rules were validated using:

```bash
sudo /var/ossec/bin/wazuh-analysisd -t
```

After successful validation, Wazuh Manager was restarted:

```bash
sudo systemctl restart wazuh-manager
```

The service was verified as active.

### Test Command

Executed on the monitored Windows endpoint:

```powershell
net user
```

### Expected Result

The refined rule should identify the user account enumeration command and generate a Rule 100101 alert.

### Observed Result

Wazuh successfully generated:

- **Rule ID:** 100101
- **Alert Level:** 8
- **Description:** EDR Lab 04: Windows user account enumeration command detected

## 9. Negative Test

A second test was performed to evaluate whether the refined rule would avoid alerting on a different command.

### Test Command

```powershell
net help
```

### Expected Result

- Rule 100100 may generate an alert because `net.exe` or `net1.exe` was executed.
- Rule 100101 should not generate a new alert because the command does not perform the targeted user account enumeration operation.


## 10. Detection Comparison

| Feature | Rule 100100 | Rule 100101 |
|---|---|---|
| Detection Type | General process execution | Specific command-line behavior |
| Event Source | Sysmon Event ID 1 | Sysmon Event ID 1 |
| Executables | net.exe / net1.exe | net.exe / net1.exe |
| Command-Line Condition | No | Yes |
| Alert Level | 6 | 8 |
| `net user` Test | Parent rule matched | Refined alert generated |
| `net help` Test | Alerts observed | No new refined alert observed |

## 11. Security Analysis

The refined detection improved precision by requiring a command-line pattern associated with Windows user account enumeration.

This reduced unnecessary Rule 100101 alerts during the controlled negative test.

However, the rule has limitations:

- It focuses on specific `net` and `net1` command-line formats.
- Other account discovery methods are not covered.
- Additional command-line variations may require further tuning.
- The laboratory did not measure false positive rates over a large event dataset.
- A user account query is not inherently malicious.

The detection should therefore be treated as an investigation signal rather than proof of compromise.

## 12. Investigation Outcome

**Status: Successfully validated**

The investigation demonstrated that a custom detection rule can be syntactically valid while failing to match actual endpoint telemetry.

The problem was resolved by examining the original Sysmon event and adapting the regular expression to the observed command-line structure.

Both positive and negative tests produced the expected results within the reviewed test windows.

## 14. Key Takeaways

Effective detection engineering requires more than writing rules.

Rules must be tested against real telemetry, validated after changes, and evaluated using both matching and non-matching scenarios.

This laboratory demonstrated how a small formatting difference in a command line can prevent an otherwise valid detection rule from generating an alert.

The final detection successfully identified the targeted behavior while avoiding a new refined alert for the tested help command.

**Final Result:** Rule 100101 successfully refined, deployed, and validated.
